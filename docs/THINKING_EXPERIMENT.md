# 让自研模型「会思考」的实验记录

> 目标：让 `nanogpt.c`（纯 C 手写的小模型）学会**分步骤做题**，而不是只会续写教材文字。
> 结论先说：**部分成功，最终未达标**。1.36M 参数版本能到约 50% 正确率，放大与屏蔽实验均失败。
> 记录时间：2026-11-22 ~ 11-23

---

## 一、为什么不能「直接让它思考」

原来那版模型（136 万参数，字符级，训了 68 万字教材）的输出是这样：

```
提示：李白的代表作
输出：• 所有从加上当于号变量的变化，而次数是原矩阵中的 形状
      • 这正是2×2缩放矩阵的行列式……
```

它完全没有「回答问题」的概念，只是在按统计规律续写。训练 loss 已经降到 0.36（基本背熟了语料），说明**不是没学会，而是学会了「续写」而不是「回答」**。

所以要让它「思考」，必须换训练目标。

---

## 二、方案：把算法写成文字，让它照着写

选了一个**可验证**的窄任务：两位数加法。

训练数据格式（每条都是完整的问答）：

```
问：86+19=?
想：个位 6+9=15，写 5，向十位进 1；十位 8+1+1=10，写 0，进 1；百位 1。
答：105
```

关键设计：
- **题目形式统一**，模型只需学一种模式
- **每一步都可验证**，对错一目了然
- **答案必须由步骤推出**，不能瞎猜

生成器：`tools/gen_think_corpus.py`

| 项目 | 数值 |
|------|------|
| 训练集 | 8800 条（一位数全部 100 种 × 10 遍；两位数+一位数全部 900 种 × 4 遍；两位数+两位数随机 4200 种） |
| 测试集 | 300 条，**训练时从未出现**的题目 |
| 字符数 | 373,572 |
| 1 epoch | 364 步（每步 1024 token） |

---

## 三、速度优化：先解决「跑得动」

同一份语料，不同编译选项和线程数（i7-12700，12 核 20 线程）：

| 编译 | 线程 | 毫秒/步 |
|------|------|---------|
| `-O2` | 4 | 1028 |
| `-O2` | 8 | 930 |
| `-O3` | 8 | 656 |
| **`-O3 -march=native`** | **8** | **464** |
| `-O3 -march=native` | 12 | 480 |
| `-O3 -march=native` | 4 | 479 |

**结论：编译优化带来 2 倍加速，线程数几乎无影响**（模型太小，并行度上不去，实际只用到 1.4~2.5 核）。

> 踩坑：`OMP_PROC_BIND=close` + `OMP_PLACES=cores` 在这颗大小核 CPU 上会报
> `libgomp: Affinity not supported`，并且实测让训练从 445 ms/步 掉到 2674 ms/步。**不要设**。

## 四、三轮实验与结果

### 实验 1：1.36M 参数（4 层 / 128 维 / 4 头 / MLP 512）

训练 3000~4500 步，loss 0.22~0.36。

**准确率：约 50%（12 题里对 6 题）**

对的样子：

```
问：77+3=?
想：个位 7+3=10，写 0，向十位进 1；十位 7+0+1=8。
答：80            ✓
```

错的样子：

```
问：86+19=?
想：个位 6+0=7，写 7；十位 8+0=8。
答：87            ✗（应为 105）
```

**失败模式：把第二个数的十位当成个位**（19 读成 10、69 读成 60、51 读成 50）。

### 实验 2：放大到 4.8M 参数（4 层 / 256 维 / 8 头 / MLP 1024）

3000 步，最终验证 loss 0.2206，耗时 73 分钟。

**准确率：0/24**

但有个诡异现象——**训练完自动生成的样例几乎全对**：

```
57+7  → 个位 7+7=14，写 4，进 1；十位 5+0+1=6。答：64   ✓
99+2  → 个位 9+2=11，写 1，进 1；十位 9+0+1=10。答：101  ✓
```

原因：那些样例是**模型自己出题、自己答**。只要题目和答案由它自己生成，就自洽；一旦给定外部题目，它就读错数字。

**这套数据让模型可以「作弊」**——它学会了生成整段问答，而不是读题作答。

### 实验 3：屏蔽题目段损失（同样 4.8M）

理论上正确的修法：训练时只对「推理 + 答案」算损失，题目部分置零，逼它必须读输入。

实现：`tools/add_prompt_mask.py`，改动 `nanogpt.c`
- 载入语料时扫描「问：…?」段，生成逐字符屏蔽表
- 采批时同步填 `ymask[]`
- `loss_and_grad()` 跳过屏蔽位置，并按有效位置数归一化

实测屏蔽比例：**82,400 字符 / 399,972 = 20.6%**

训练 3000 步，**验证 loss 0.077（极低）**，耗时 6.6 小时。

**准确率：0/4，且输出退化**

```
问：86+19=?
输出：个位 6+1=7，写 7；十位 9+0=9。答：97  答：19  想：个位 1+0=1……答：151
```

它开始连续输出多个「答：」，结构崩坏。

> 中途误判：第 450 步时曾看到「86+19 → 个位 6+9」，以为屏蔽生效。那是巧合，完整训练后反而更差。

## 五、结论

| 版本 | 参数量 | 训练 | 准确率 | 状态 |
|------|--------|------|--------|------|
| v1 | 136 万 | 3000 步 | **约 50%** | 最好 |
| v2 | 482 万 | 3000 步 | 0% | 会自编自答，不读题 |
| v3 | 482 万 + 屏蔽 | 3000 步 | 0% | 退化，输出多答案 |

**根本瓶颈是架构，不是训练技巧：**

1. **字符级 + 4 层的注意力装不下「位置绑定」**——把输入第 2 个位置的字复制到输出第 8 个位置，这需要 induction head 一类的机制，小模型学不出来。
2. **加大模型反而更糟**：容量被用来学「表面的问答模式」，不是「条件依赖」。
3. **屏蔽题目理论上正确，但小模型学不出条件依赖**，只会退化。

---

## 六、这次实验证明了什么

**成立的：**

- 手写的 C 训练代码是对的：前向、反向、AdamW、SwiGLU、RoPE 全部经梯度检查验证
- 字符级小模型可以学会**固定格式的分步骤推理**（步骤、进位、报答案都对）
- 1.36M 参数在窄任务上能到 50%，说明「小模型做窄任务」这条路本身是通的

**不成立的：**

- 靠加大参数（4.8M）提升「读题能力」——无效
- 靠屏蔽损失逼迫条件依赖——在这个规模上无效

---

## 七、如果要继续

按性价比排序：

1. **换数字表示**：把 `86` 当成一个 token 而不是两个字符，大幅降低绑定难度
2. **扩到 1 亿参数 + GPU**：CPU 上 4.8M 就要 1 小时/3000 步，1 亿参数需要 GPU
3. **改用现成的 tokenizer + 预训练权重初始化**：从零训字符级模型，样本效率极低
4. **接受「窄任务小模型」定位**：只做一位数加法/减法，准确率能到很高，但价值有限

---

## 八、复现方式

```bash
# 1. 生成语料（训练集 + 测试集）
python tools/gen_think_corpus.py

# 2. 编译（8 线程、O3、native 最快）
gcc -O3 -march=native -fopenmp -DCHARLEVEL \
    -DNLAYER=4 -DNEMBD=256 -DNHEAD=8 -DMLP=1024 \
    -o nanogpt src/nanogpt.c -lm

# 3. 训练 3000 步
set OMP_NUM_THREADS=8
nanogpt train think_corpus.txt 3000 think.bin 4

# 4. 评测（训练时没见过的题）
python tools/eval_think.py think.bin 24

# 5. 按难度分组评测
python tools/eval_think_by_level.py
```

文件对应：

| 文件 | 作用 |
|------|------|
| `tools/gen_think_corpus.py` | 生成加法推理语料（含训练/测试划分） |
| `tools/eval_think.py` | 用测试集算准确率 |
| `tools/eval_think_by_level.py` | 按一位数/两位数分组评测 |
| `tools/add_prompt_mask.py` | 给训练加题目屏蔽（实验 3） |
| `src/nanogpt.c` | 训练主体，已支持屏蔽 |

---

## 九、诚实的一句话总结

**我们让一个 136 万参数的 C 模型学会了「像模像样地分步做加法」，一半的题能算对；但它始终学不会可靠地读题——这不是训练不够，是这个规模的模型装不下这种能力。**
